02

数据与特征工程

从 30 万行原始遥测到 18 维段级特征的关键转换

ESA OPS-SAT-AD 数据集

数据来自 ESA OPS-SAT 卫星的公开遥测异常检测数据集（OPS-SAT-AD）。数据集包含 2,123 个遥测段，每段是一段时间内某个通道的连续采样值。

文件规模说明
segments.csv303,493 行 × 8 列原始遥测数据，每个数据点包含时间戳、通道、采样值
dataset-*.csv2,123 行 × 23 列段级特征数据集，18个特征 + 5个元数据列
📐
数据集特点

异常比例 20.4%（正常 1689 / 异常 434），数据已预标注。训练集和测试集由官方 train 列划分。

9 个遥测通道：卫星的"感官"

每个通道是卫星上的一个物理传感器，就像人体的不同感官。每个传感器测量不同的物理量：

🧲

强通道 — 磁力计

CADC0872/73/74
测量 X/Y/Z 轴磁场强度，反映卫星姿态。异常可能意味着姿态偏转或外部磁干扰。

☀️

弱通道 — 光电二极管

CADC0884~894
6个太阳敏感器，用于确定卫星相对太阳的角度。异常可能是遮挡或姿态控制问题。

18 维段级特征：把波形变成数字

每个遥测段是一段时间序列。我们需要把它压缩成一组数字（特征），让机器学习算法能理解。

mean段内平均值 — 整体水平偏高还是偏低
var / std方差 / 标准差 — 波动幅度大不大
kurtosis峰度 — 有没有极端尖峰
skew偏度 — 分布是否对称
n_peaks峰值数量 — 信号跳变几次
smooth10/20_n_peaks平滑后的峰值数 — 去噪后的趋势
diff_peaks / diff2_peaks一阶/二阶差分峰值 — 变化率的突变
diff_var / diff2_var差分方差 — 变化的剧烈程度
gaps_squared时间间隔平方和 — 采样是否均匀
duration / len时长 / 数据点数 — 段的规模
len_weighted采样率 × 长度 — 归一化后的段规模
var_div_duration / var_div_len方差除以时长/长度 — 归一化波动

03

Isolation Forest 异常检测

用"随机切割"来发现异常——从全局到分通道的三阶段演进

什么是 Isolation Forest？

想象你在一个大房间里随机放隔板。正常人聚在一起，需要很多次隔板才能隔开；而离群的人站得远，几次隔板就被单独隔离了。Isolation Forest 就是这个原理。

🌲
核心思想

异常点因为和大多数数据"不一样"，在随机树中被隔离所需的切割次数更少。隔离路径越短 → 越可能是异常。

CODE 
from sklearn.ensemble import IsolationForest

model = IsolationForest(
    contamination=0.2,
    n_estimators=100,
    random_state=42
)
model.fit(X_train)
preds = model.predict(X_test)
PLAIN ENGLISH

从 scikit-learn 库导入 Isolation Forest 算法

创建一个模型实例：

contamination=0.2 — 预期数据中约 20% 是异常

n_estimators=100 — 构建 100 棵随机树

random_state=42 — 固定随机种子，保证结果可复现

用训练数据"学习"正常数据长什么样

对测试数据做预测：返回 1（正常）或 -1（异常）

三阶段演进：F1 从 0.30 到 0.57

我们不是一步到位的。通过三次方法迭代，F1 分数提升了 89.7%。

0
全局 IForest — F1 = 0.2996

把所有 9 个通道的数据混在一起训练一个模型。问题：不同通道的数据分布差异巨大，"混为一谈"效果很差。

1
分通道独立 IForest — F1 = 0.5381 (+79.6%)

每个通道单独训练一个 Isolation Forest。磁力计和光电二极管的"正常"范围完全不同，分开建模后精度大幅提升。

2
IF + 统计规则融合 — F1 = 0.5683 (+89.7%)

在 Isolation Forest 的基础上，叠加 3σ 规则和 IQR 规则。两种方法取并集——只要任一方法判定为异常，就标记为异常。

💡
关键洞察

分通道建模是最大的提升来源（+79.6%）。不同物理传感器的数据分布差异极大，用一个模型"一锅端"必然效果差。这是我们在架构设计上最重要的决策。

代码解读：统计规则融合

CODE 
def sigma_rule(value, mean, std, n_sigma=3.0):
    return abs(value - mean) > n_sigma * std

def iqr_rule(value, q1, q3, iqr_val, k=1.5):
    lo = q1 - k * iqr_val
    hi = q3 + k * iqr_val
    return value < lo or value > hi
PLAIN ENGLISH

3σ 规则：如果一个值距离平均值超过 3 倍标准差，就判定为异常

这就像说"身高超过 2.3 米的人很少见"

IQR 规则：用四分位距来划定"正常范围"

计算下界 Q1 - 1.5×IQR 和上界 Q3 + 1.5×IQR

如果值超出这个范围，就判定为异常

两种规则互补：3σ 对正态分布有效，IQR 对偏态分布更鲁棒

RAG 智能解释系统

检索增强生成 — 让 AI 结合卫星手册知识来回答"为什么异常"

RAG 是什么？为什么需要它？

单独的大语言模型（如 DeepSeek）不知道我们这颗卫星的具体技术细节。RAG 的核心思想是：先检索相关文档，再让 AI 基于这些文档回答。

1
构建知识库

把卫星手册、技术文档（PDF/MD）切分成小块（chunk），用 BGE-M3 模型转成向量，存入 FAISS 索引。共 2,847 个知识块。

2
检索（Retrieval）

用户查询（如"磁力计X轴异常"）也转成向量，在 FAISS 中找最相似的 Top-5 知识块。相似度越高越相关。耗时约 50ms。

3
生成（Generation）

把检索到的知识块作为上下文，配合精心设计的 Prompt，交给 DeepSeek V3 生成结构化诊断报告。耗时约 2-5s。

RAG 系统架构：组件对话

Pipeline

收到异常检测结果：CADC0872 磁力计X轴，段 #456，异常分 0.87。开始 RAG 诊断流程。

Prompt 工程：精确控制 AI 输出

RAG 的效果不仅取决于检索质量，更取决于 Prompt 工程的设计。我们的系统提示词规定了严格的 7 段输出格式：

【通道定位】该通道的物理含义和在卫星中的角色
【异常类型】跳变 / 持续偏离 / 周期波动 / 噪声增大等
【可能原因】最多3条，按可能性降序排列
【影响评估】最多2条，对卫星运行的影响
【建议措施】最多2条，地面运维人员的操作建议
【紧急程度】仅一个词：低/中/高/紧急
【来源】[文档名 p.页码] 格式引用知识库来源

代码解读：向量检索

CODE 
def search(self, query, top_k=5):
    q_emb = self.embedder.encode([query])
    scores, ids = self.index.search(
        q_emb.astype('float32'), top_k
    )
    results = []
    for score, idx in zip(scores[0], ids[0]):
        meta = self.document_metadata[idx]
        results.append({
            "content": meta["content"],
            "score": float(score),
        })
    return results
PLAIN ENGLISH

搜索函数：输入查询文本，返回最相似的知识块

先用 BGE-M3 把查询文本编码成向量（数字数组）

在 FAISS 索引中做向量相似度搜索，找 Top-K 个最相似的

FAISS 返回相似度分数和文档编号

遍历结果，把每个匹配的文档内容和分数打包

返回结果列表——每个元素包含文档内容和相似度分数

实验评估与特征分析

用数据说话：哪些特征最重要？模型效果如何量化？

评估指标体系

我们用多个指标从不同角度衡量模型效果：

🎯

F1 Score

精确率和召回率的调和平均。F1 = 2 × P × R / (P + R)。我们的最佳值 0.568。

📐

Precision

被判定为异常的段中，真正异常的比例。越高说明"误报"越少。

🔎

Recall

所有真正的异常段中，被检测出来的比例。越高说明"漏报"越少。

⚠️
为什么 F1 只有 0.568？

Isolation Forest 是无监督算法——它不使用标签信息训练。在异常检测任务中，无监督方法的 F1 通常在 0.3-0.6 之间，我们的结果已经显著优于基线（+89.7%）。要突破 0.6 需要引入有监督方法（如 XGBoost），这超出当前项目范围。

特征贡献度分析

我们用两种方法分析哪些特征对异常判定贡献最大：

1
IForest 分裂频率统计

统计 100 棵随机树中，每个特征被用作分裂节点的次数。被用得越多 → 该特征越能区分正常和异常。

2
Permutation Importance

随机打乱某个特征的值，观察 F1 下降多少。F1 下降越多 → 该特征越重要。这是更可靠的方法。

🏆
发现

kurtosis（峰度）、diff2_var（二阶差分方差）和 n_peaks（峰值数）是最重要的特征。这说明异常段的主要信号特征是：存在极端尖峰、变化率剧烈波动、以及频繁的数值跳变。

代码解读：特征重要性计算

CODE 
def compute_iforest_importance(model, feature_names):
    split_counts = np.zeros(len(feature_names))
    for tree in model.estimators_:
        feature_indices = tree.tree_.feature
        valid = feature_indices >= 0
        for fi in feature_indices[valid]:
            split_counts[fi] += 1
    importances = split_counts / split_counts.sum()
    return importances
PLAIN ENGLISH

计算 IForest 内置特征重要性

创建一个数组，记录每个特征被用了多少次

遍历模型中的每一棵树

获取这棵树每个节点用的是哪个特征来分裂数据

-2 表示叶子节点（不需要分裂），跳过

对每个有效分裂节点，给对应特征的计数 +1

最后归一化（除以总数），得到每个特征的重要性比例

🧠 算法与模型

Q1: F1=0.5683，这个数字到底好不好？

记住三句话：

① 我们的异常比例是 20.4%，如果全部猜"异常"，F1 大概只有 0.34；

② 我们的 0.5683 比这个"无脑猜"提升了大约 67%，说明模型真的学到了东西；

③ 无监督算法在这个数据集上，F1 在 0.3~0.6 之间都是正常范围，我们的结果属于中上水平。

Q2: contamination=0.2 和真实异常比例 20.4% 几乎一样，你是不是偷看标签了？

坦诚回答，分两种情况：

① 如果是——那就诚实说"我们参考了数据集的已知异常比例来设定"，这其实叫半监督设定，不算丢人；

② 如果想证明参数不敏感——可以补一个实验：把 contamination 从 0.1 调到 0.5，看 F1 变化大不大，如果波动不超过 5%，说明模型对这个参数不敏感；

③ 关键是要诚实，评委要听的不是完美答案，而是你有没有思考过这个问题。

Q3: 统计规则和 IForest 取"并集"，为什么不取"交集"？

打个比方你就懂了：

① 取并集 = "只要有人说可疑就标记"，好处是漏报少（recall 高），坏处是误报多（precision 低）；

② 取交集 = "所有人都说可疑才标记"，好处是误报少，坏处是漏报多；

③ 我们选并集是因为卫星遥测场景下，漏报一个真正异常的代价比多查几个误报高得多——宁可多查不可漏查；

④ F1 从 0.5381 到 0.5683 只提升了 3%，说明并集确实牺牲了 precision，但 recall 提升明显，这是有意的权衡。

Q4: 9 个通道各训各的，磁力计三轴明明是同一个传感器，这样合理吗？

这是我们的一个已知局限，可以这样回应：

① 分通道训练是因为不同传感器的"正常范围"差异很大，混在一起反而互相干扰；

② 但确实丢失了跨通道信息——比如三轴磁力计同时偏移，分开看每轴变化不大就漏掉了；

③ 未来改进方向：可以加一些"跨通道特征"，比如通道间相关系数、协方差等，作为第 19、20 维特征加入。

Q5: 你说"峰度"最重要，但 IForest 的特征重要性和真正的"异常相关性"是一回事吗？

不是一回事，要区分清楚：

① IForest 的重要性说的是"这个特征在切割数据时被用得多不多"，反映的是数据分布特征，不直接等于"和异常有关"；

② Permutation Importance 是"打乱这个特征后 F1 下降多少"，这个才真正和检测效果相关；

③ 好消息是两种方法排出来的 top 特征基本一致（都是峰度、差分方差、峰值数），说明结论是靠谱的。

🔍 RAG 与创新性

Q6: 为什么用 RAG 而不是直接让 ChatGPT 回答？

一句话概括：RAG = 先查资料再回答，不是凭空编。

① 直接问大模型"磁力计异常怎么办"，它会给你一个通用回答，但不知道我们卫星的具体情况，甚至可能编造信息；

② RAG 会先从我们的卫星手册里找到相关段落，再基于这些真实文档生成回答，有据可查；

③ 我们的诊断报告里有"来源"字段，标注了参考了哪个文档第几页，可以直接溯源验证。

Q7: 知识库切成 512 字一块、取 top-5，这些数字怎么来的？

这些参数是有依据的，记住几个关键点：

① chunk_size=512：BGE-M3 模型的输入上限是 512 token，切太大模型处理不了，切太小上下文不完整；

② top_k=5：太少（比如 1）信息不够，太多（比如 20）噪声太大，5 是经验和实验的平衡点；

③ chunk_overlap=50：相邻块重叠 50 字，防止一句话被切断在两个块里；

④ 这些参数确实可以进一步用网格搜索优化，目前是基于经验和文献推荐的合理起点。

Q8: 如果检索出来的文档看着相关但内容是错的，怎么办？

这是 RAG 的一个已知风险，目前的应对方式和未来改进：

① 当前：靠 DeepSeek 模型自身的判断力来过滤，Prompt 里写了"无依据写知识库未覆盖"；

② 当前：score_threshold=0.3 过滤掉相似度太低的结果，减少噪声；

③ 未来改进：加一个"重排序"步骤，用更精细的模型对 top-5 结果做二次筛选；

④ 未来改进：如果多个知识块互相矛盾，系统应该显式提示"存在不确定性"，而不是强行给一个答案。

Q9: LSTM、Transformer 都能做异常检测，你们的方案有什么不一样？

一句话区分：别人只能告诉你"有异常"，我们还能告诉你"为什么"。

① LSTM/Transformer 等时序模型：擅长检测数值上的异常模式，但输出就是"异常/正常"，没有解释；

② 知识图谱方案：能解释，但需要专家手动构建图谱，维护成本很高；

③ 我们的 RAG 方案：只要把文档扔进知识库就能用，不需要手动建图谱，兼顾了解释性和低成本；

④ 我们的核心创新就是"检测+解释"的闭环——先用 IForest 发现异常，再用 RAG 解释原因。

⚙️ 系统与工程

Q10: 前端所有代码都写在一个文件里，这不是很乱吗？

承认问题，说明原因和改进计划：

① 目前是项目原型阶段，单文件开发速度快，方便快速迭代和调试；

② 项目总共只有 3 个人，没有多人协作冲突的问题，单文件是务实的选择；

③ 如果要继续扩展，重构路径很清楚：用 React Router 拆页面，用 Context 管状态，把图表组件抽出来复用。

Q11: 每次打开页面都要重新读 30 万行 CSV，不会卡吗？

这是一个已知的性能问题，分层解决：

① 目前数据量不大（30 万行约 30MB），本地开发环境下 pandas 读取大概 1-2 秒，体感不明显；

② 但确实没有缓存，如果多人同时访问会重复读取，存在优化空间；

③ 最简单的改进：启动时一次性加载到内存，后续请求直接用内存数据，不需要反复读文件；

④ 如果数据量再大，可以换成 SQLite 数据库，用索引加速查询。

Q12: 如果 RAG 的 LLM 调用失败了，系统会怎样？

我们的策略是"降级但不崩溃"：

① LLM 挂了 → 检测功能照常工作，只是诊断报告变成固定提示"RAG 引擎暂不可用"；

② 嵌入模型挂了 → 返回零向量，检索结果为空，不会报错崩溃；

③ 这样设计是因为：演示和开发阶段，一个模块挂了不应该拖垮整个系统；

④ 如果上生产环境，需要改进：加告警通知、区分"无异常"和"系统故障"两种状态，避免误判。
